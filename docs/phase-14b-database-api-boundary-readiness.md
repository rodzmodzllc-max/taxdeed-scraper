# Phase 14B: Database/API Customer Boundary Design & Migration Readiness Gate

**Status:** Phase 14B (Database/API Customer Boundary Design & Migration Readiness Gate), 2026-09-14. Companion to `docs/production-data-contract.md` (Phase 13), `docs/phase-14a-customer-safety-hardening.md` (Phase 14A — first named this gap and proposed migration 005), and `docs/commercial-data-inventory.md`. This phase does not execute migration 005 or any other production change. It answers, from the actual current repository, exactly what the customer/API data boundary should be before 005 is ever run, audits 005 itself for completeness, and — because 005 alone is not sufficient — designs a fully-specified, unexecuted companion migration (`005a`).

## 0. Answers to the ten framing questions

1. **What database read surfaces currently expose `public.properties`?** Four real ones: `get_properties()` RPC, the unscoped `select("*")` fallback (both via `public/app.js`), any other authenticated client hitting `/rest/v1/properties` directly, and `digest_candidates()` (service-role only, not customer-facing). See Section 1.
2. **Which are customer-facing?** `get_properties()`, the `select("*")` fallback, and any third-party authenticated REST caller. Not `digest_candidates()`.
3. **Which are internal/admin-only?** `digest_candidates()` (service_role, scheduled job only) and `scripts/export_backup.py` (service_role, GitHub Actions artifact, not a database read surface in the PostgREST sense but a full-row export worth naming — Section 1).
4. **Which columns are legitimately customer-visible?** The ~46-column list Phase 13/14A already established, **plus `harvester_source`** — re-verified this phase against actual rendering/export code, with two corrections: `gone_since`'s raw value IS rendered on cards (Phase 14A's doc said it wasn't), and `harvester_source` is now genuinely read by the frontend (`assessedSourceLabel()`, added within Phase 14A itself) and so is customer-safe, not internal (Section 2's notes — this second correction caught a latent bug in migration 005 as originally written).
5. **Which columns must never be exposed through the customer contract?** `ledger_type`, `fdor_enriched_at` (re-confirmed, zero real property-access references in `app.js`), plus the still-unidentified geometry column (Section 2, bucket E — fails closed).
6. **Does migration 005 actually close the relevant exposure?** No — it closes only the RPC path. The raw-table path (`select("*")` fallback and any other authenticated REST caller) remains fully open after 005 alone. Section 3.
7. **What is the smallest safe database/API change required?** A column-level `GRANT`/`REVOKE` on the base table (no RLS change, no new database object) — designed, not executed, as `scripts/migrations/005a_close_direct_properties_grant.sql`. Section 4/5.
8. **Can the application continue functioning after the proposed boundary change?** Yes, provided 005 and 005a are applied together and in that order — verified by tracing `get_properties()`'s `security invoker` semantics (Section 3's key finding) and by the fact that every column 005a grants is already the same list 005/the CSV export use. Section 5.
9. **What exact production verification must be performed after migration?** A four-point smoke test plus a live RLS/grant confirmation, spelled out in `005a`'s own MIGRATION STEPS section and repeated in Section 7 below.
10. **Is the repository READY for migration execution?** **Not yet — READY_WITH_LIMITATIONS, pending live verification this sandbox cannot perform.** Section 8.

## 4. Smallest correct architecture (Step 4)

Working through the eight layers the phase instructions name:

1. **Database table** — currently grants blanket `SELECT` on every column to `anon`/`authenticated`. This is the actual point of narrowing; everything downstream depends on it.
2. **RLS** — already correctly scoped (row-level, `is_approved()`) and, per this phase's hard rule, not to be touched. Layers 1 and 2 are independent primitives in Postgres — a column-level `GRANT` change requires no RLS change and creates no new policy.
3. **Customer RPC** (`get_properties()`) — 005 already narrows this correctly, **but** because it is `security invoker`, its correctness after 005 is contingent on layer 1 also being narrowed to at least the same column set, or on layer 1 being left alone (today's state). If layer 1 is narrowed to a column set narrower than what `get_properties()`'s body selects, the RPC breaks. This is the ordering dependency Section 5 makes explicit.
4. **Frontend** — already reads only the ~46-column contract; no change needed here regardless of which database-layer option is chosen.
5. **CSV export** — same as frontend.
6. **Future API export** — `digest_candidates()` is already correctly isolated (service_role, fixed projection); no change needed.
7. **Internal harvester/sync path** — uses `service_role`, which bypasses both RLS and ordinary grants; unaffected by any customer-boundary change at layers 1-3.
8. **Admin/operations access** — not investigated further this phase beyond noting `export_backup.py`'s broader artifact-visibility question (Section 1) — that question sits outside the database/API layers this phase's principle diagram (INTERNAL INGESTION → DATABASE → CUSTOMER-SAFE READ BOUNDARY → FRONTEND/EXPORT/API) is about, since it is a CI-artifact channel, not a database read.

**Conclusion: the current architecture cannot provide a genuinely safe customer boundary through the RPC layer alone.** Layer 3 (005) is necessary but not sufficient; layer 1 (a column-level grant change) is the missing piece, and it can be added without touching layer 2 (RLS) at all. This directly answers the instruction's own caution: *"If the current architecture cannot provide a genuinely safe customer boundary without RLS or a dedicated projection, state that clearly."* It does not require RLS — it requires a dedicated column-level grant, which is a narrower, less risky primitive than either a new RLS policy or a base-table `REVOKE`-and-view swap (Section 5 explains why the view-swap alternative was considered and set aside).

## 5. Migration 005a design (Step 5)

**`scripts/migrations/005a_close_direct_properties_grant.sql`** — proposed, fully specified, **not executed**. Full content committed for review; summarized here (see the file itself for the complete WHY REQUIRED / CURRENT LIMITATION / VERIFICATION REQUIRED / TARGET ARCHITECTURE / MIGRATION STEPS / ROLLBACK / DATA-SAFETY / TEST PLAN sections):

- **Mechanism**: `REVOKE SELECT ON public.properties FROM anon, authenticated;` followed by `GRANT SELECT (<the same ~46-column list 005/the CSV export already treat as authoritative>) ON public.properties TO authenticated;`. `anon` receives no grant at all (RLS already fully blocks it from any real row; this makes the grant match that reality rather than over-granting a role that never got usable data anyway).
- **Why not a `REVOKE`-and-view swap (005's own "option a/b")?** Both of 005's own named options assume `get_properties()` can simply be pointed at a narrower object. But `get_properties()` is `security invoker` — it executes with the *caller's* privileges, not the function owner's. If `authenticated`'s table-level `SELECT` were revoked outright with nothing re-granted at the table level, `get_properties()` itself would start failing for every caller, since an invoker-rights function cannot read a column its caller isn't allowed to read, even from inside the function body. Column-level `GRANT` avoids this entirely: `authenticated` keeps real, direct table access, just narrowed to the same column set `get_properties()` already needs — so the RPC keeps working with no additional change, and the raw-table path is closed to the same column set at the same time, via a single mechanism.
- **Why this doesn't need RLS**: column-level `GRANT` is evaluated by Postgres before RLS is even reached — a role either has `SELECT` on a column or it doesn't; RLS only narrows which *rows* a role that already passed the column check gets back. This satisfies the phase's hard rule against creating RLS policies by construction, not by omission.
- **Critical ordering dependency, found this phase**: 005a must run *after* 005, never standalone or before it. If 005a's grant narrowing were applied while `get_properties()` still has its live, unmigrated `select *` body, the RPC would immediately break for every caller (the function would try to select columns its caller no longer has privilege on). This is a real, production-breaking sequencing risk if the two files were ever applied out of order or independently — documented explicitly in 005a's own header, not left as an inference a future operator would have to make correctly under pressure.
- **What could not be verified this phase, and is required before either file runs**: the *live* RLS policy set on `public.properties`, and the *live* current grants for `anon`/`authenticated`. Both `mcp__Supabase__list_tables` and `mcp__Supabase__execute_sql` were denied by this environment's production-reads classifier (same denial as Phase 14A — re-attempted this phase, not assumed still true). `mcp__Supabase__get_advisors` (a permitted read) was re-run and confirms the security-advisory findings are unchanged from Phase 14A (same RLS-enabled-no-policy tables, same `function_search_path_mutable` list including `get_properties`/`properties_sync_geom`, same `postgis`-in-public warning, same SECURITY DEFINER findings). It does not, and cannot, enumerate `pg_policies` or `information_schema.role_column_grants` directly. **A genuine, newly-found gap**: this repository's tracked migration history contains a RESTRICTIVE `is_approved()` policy on `properties` (`schema-v6-approvals.sql`) but **no PERMISSIVE policy for it anywhere** — yet the application demonstrably serves real property data to approved users in production today. Per Postgres RLS semantics (and CLAUDE.md's own documented 2026-08-24 outage lesson: a RESTRICTIVE-only table with zero PERMISSIVE policies returns empty results for everyone), a PERMISSIVE policy allowing approved users to read `properties` **must exist live** but is not captured anywhere in this repository's git history — the same "tracked files don't fully describe the live schema" gap Phase 13/14A already found for several columns and the geometry function, now confirmed (by this specific absence, not by assumption) to extend to RLS policy text as well. This does not block 005a's design (it touches no RLS, so it doesn't need to know this policy's exact text) but it does mean 005a's own VERIFICATION REQUIRED section is not optional formality — it names a real, confirmed-present gap in what this session can verify from the repository alone.
- **Per Step 5's own stop condition** ("If RLS cannot safely be implemented without knowing the application's authentication model, STOP and document that blocker rather than guessing"): this phase did not attempt to design any RLS change, so that specific blocker does not apply to 005a. It is recorded here anyway because it is the honest reason a *view-swap or RLS-based* alternative was not pursued instead of the grant-based design — not guessed around, avoided by choosing a mechanism that doesn't need the missing information.
